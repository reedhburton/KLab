## Hidden Debian resolver issue

The queue asked for `debian:bookworm:6.1:*`, but resolved those rows to `6.12.107+deb12-*` because the family filter used `^6\.1`, which also matches `6.12`.

r4 changes family matching to require a version delimiter after the requested family. Thus 6.1 matches 6.1.x but not 6.12.x. The r4 retry performs a resolver-only Bookworm 6.1 check rather than rebuilding all successful Debian targets.

## Fedora exact diagnosis

The r3 stdout/path contamination bug is fixed: the logs now progress through exact historical GCC/binutils/make acquisition.

Remaining failures split into two classes.

### Fedora 20/23

The original Koji buildroot repos have expired. KLab has a reconstructed local package repo, but the metadata was generated by a modern `createrepo_c`. The vintage yum/dnf clients fail to load it, causing KLab to fall toward release repositories; F20 additionally showed that the failed exact Koji repo remained enabled during this fallback.

r4:

- regenerates reconstructed repo metadata with `createrepo_c --compatibility --database --general-compress-type=gz`;
- upgrades already-cached fallback repos in place (no RPM redownload) using a `REPODATA-COMPAT-V2` marker;
- explicitly disables failed Koji repos when using release fallback.

### Fedora 29/42/43/44

The reconstructed Koji repository itself is usable. The failure came from installing every captured kernel RPM. Runtime/debug/selftest packages then requested dependencies irrelevant to external-module compilation (dracut, firmware, keyutils, iproute-tc, nmap-ncat, etc.).

r4 installs only:

- kernel-devel
- kernel-headers
- kernel-rpm-macros
- kernel-srpm-macros

The exact Koji compiler/binutils/make RPMs remain pinned and installed separately.

## CentOS Stream 9/10 diagnosis

The buildenv installer requested the full `coreutils` package in minimal CentOS Stream containers that already provide `coreutils-single`. DNF correctly rejected the mutually exclusive package transaction. The capture shell did not stop immediately, so Kbuild proceeded without a successfully installed `kmod`; the smoke module built, but `modinfo` was absent, producing a misleading `vermagic missing` rc=42.

r4:

- no longer explicitly requests `coreutils` in RPM buildenv capture;
- accepts the container's existing `coreutils-single` implementation;
- makes setup/package installation fail-fast;
- temporarily disables `set -e` only around the smoke `make` so the original Kbuild return code is still preserved.

## Retry policy

`klab-daytime-retry-r4.sh` is deliberately narrow:

- Fedora 20/23/29/42/43/44
- CentOS Stream 9 and 10 exact cached targets
- Debian Bookworm 6.1 resolver check

Fedora uses `KLAB_REFETCH=0`. Existing kernel targets and reconstructed Koji RPM caches are reused. Old fallback repo metadata is upgraded in place instead of redownloading the package closure. Fedora 29 and 44 still force the reconstructed fallback path.

The successful Oracle/Amazon/openSUSE/Rocky/Alpine and other prior distro cases are not rerun.
